# PostgreSQL: хранение и восстановление состояния

Код — `backend/app/storage/`. БД необязательна: без `DATABASE_URL` (или если БД недоступна при старте) сервис работает как раньше — состояние в памяти, настройки/аккаунты/справочник сотрудников в JSON-файлах; с БД они хранятся в PostgreSQL (см. «Аккаунты, справочник сотрудников, настройки»).

## Как пишется

- `storage/db.py` — один фоновый поток и одна очередь (10 000 операций). Операция — `fn(conn, *args)` в транзакции. Порядок записи = порядок постановки.
- Горячий путь (`POST /plan`, события, отметки) только снимает поверхностную копию состояния под `store.lock` и ставит операцию в очередь; сериализация и SQL — в потоке записи.
- Обрыв связи: переподключение с паузой 1→30 с, та же операция повторяется (не теряется, не переставляется). Ошибка в данных — лог и пропуск (`failed`). Переполнение очереди — запись отбрасывается (`dropped`, предупреждение раз в минуту).
- Снимок дня пишется с `coalesce_key`: при серии событий в очереди выполняется только последний (`coalesced`).
- При останове процесса очередь дописывается до `DB_FLUSH_ON_EXIT_SEC` (10 с).
- Счётчики и версия схемы: `GET /ui/history/storage` (там же итог восстановления при старте).

## Миграции

`storage/migrations/NNNN_имя.sql`, применяются при подключении под `pg_advisory_lock`, каждая в своей транзакции; применённые записываются в `schema_migrations(version, name, applied_at)`. Все миграции идемпотентны (`IF NOT EXISTS`), поэтому база с таблицами старого журнала (до версионирования) принимает v1 без потери данных. Новая миграция — следующий номер, новый файл.

## Таблицы

| Таблица | Ключ | Что хранит |
|---|---|---|
| `days`, `plan_versions`, `events`, `alerts` (v1) | date + … | журнал истории (`journal.py`, `/ui/history/*`) |
| `inputs` | sha256 | тела `PUT /reference` и `/reference/travel-matrix` (zlib), без дублей |
| `service_state` | key | `reference` → `{sha256, gen}`, `matrix` → `{sha256}`; `gen` меняется при каждом `PUT /reference` |
| `day_state` | date | последний снимок `DayState`: наряды, `arrived_at`, отмены, `visit_end_overrides`, отсутствующие, принятые события, текущий план, режимы планировщика (`payload`); `load_id` (поколение загрузки дня), `ref_gen`, `scenario` (`api` / `demo:<сценарий>`), `plan_version`, `demo` (состояние дня, загруженного из каталога данных через `/ui/demo/*`; имена колонок и путей технические) |
| `marks` | load_id, mark_key, kind | отметки сотрудников (`mark_key` = order_id или `@staff:<id>`), автор, `event_sent`/`event_id`, исходная запись в `payload`; откат удаляет строку |
| `actions` | id | изменяющие запросы `/ui/*` (и служебный `GET /ui/demo/load`): время, логин, метод+шаблон пути, путь, статус и query; тела не пишутся |
| `accounts` | login | запись аккаунта целиком (scrypt-хэш, соль, `disabled`, `must_change_password`, `token_epoch`, `pw_source`) — `auth.py` |
| `staff_profiles` | staff_id | `{"profile": {ФИО, телефон, должность, табельный номер, заметка…}, "equipment": {equipment_start, equipment_capacity} \| null}` — профиль и переопределение «рюкзака АО» одной строкой — `staff_directory.py` |
| `settings` | key | `auth_secret` → `{"secret": hex}` (секрет подписи токенов; `AUTH_SECRET` из env приоритетнее), `runtime_overrides` → `{ключ: значение}` режимов планировщика — `runtime_settings.py` |

## Восстановление при старте

`create_app()` → `storage/restore.py` (если БД задана, `STATE_RESTORE` ≠ `off` и состояние пустое; БД ждём `STATE_RESTORE_WAIT_SEC`, по умолчанию 5 с):

1. справочники и матрица из `inputs` по указателям `service_state` (те же проверки, что в PUT);
2. дни из `day_state` текущего поколения справочников (`ref_gen`) — `DayState` целиком, режимы планировщика (пробки/совместные наряды) на день;
3. если журнал ушёл дальше снимка (`max(plan_versions.version)` > `day_state.plan_version`), недостающие события из `events` проигрываются через `post_event` — `plan_version` не откатывается;
4. отметки дня (`marks` по `load_id`) — в кэш `employee_api`; состояние загрузки дня из каталога данных (`order_info` строится заново из нарядов дня и файлов каталога `UI_DATA_DIR`).

Отдельный «контекст планировщика» сохранять не нужно: `apply_event` строит `DayContext` из `DayState` при каждом событии, поэтому первое событие после рестарта обрабатывается как обычно, без пересборки дня.

Повреждённый день — лог и пропуск этого дня; ошибка целиком — пустой старт. БД недоступна — пустой старт, запись в очереди дождётся подключения.

## Аккаунты, справочник сотрудников, настройки

Общий механизм — `storage/repos.py`: `pg_repo(table)` возвращает `PgRepo` (кэш в памяти + очередь записи), если БД настроена и ответила при первом обращении (ждём `5` с один раз, потом `0,3` с), иначе `None` — модуль остаётся на своём JSON-файле. Модули предзагружаются при старте (`create_app`), поэтому ожидание БД не попадает в первый запрос.

- **Запись.** Операции управления (reset-password, disable/enable, смена пароля, правка/создание сотрудника, рюкзак АО, `PUT /ui/settings`) кладут в очередь только изменившиеся записи и ждут их записи до 3 с (`repos.flush`, вне блокировок, горячий путь не затрагивается). Если БД недоступна: запрос не падает, логин и права работают по кэшу, в логе предупреждение, запись остаётся в очереди и догоняет после подключения (до `QUEUE_MAX`).
- **Импорт файлов.** При первом старте с БД, если таблица пуста (для настроек — нет ключа), а файл есть — `auth_accounts.json`, `auth_secret.key`, `staff_directory.json` (профили + `equipment_overrides`), `runtime_settings.json` один раз импортируются; в логе `[storage] …: импортировано N`. Повторный старт ничего не импортирует. Файлы не удаляются и не меняются (в режиме БД в них больше не пишется). Импорт переносит записи как есть (ФИО, телефоны, табельные номера, переопределения рюкзаков, хэши паролей): ничего не пересоздаётся. Нет ни таблиц, ни файлов — справочник сотрудников пуст, есть только диспетчер из `DISPATCHER_LOGIN`/`DISPATCHER_PASSWORD` (иначе случайный пароль в логе).
- **Наполнение из справочника в Store.** Записи `staff_profiles` и аккаунты сотрудников создаются не из файлов, а при каждой загрузке справочников (`PUT /api/v1/reference`, «Создать день» с подгрузкой из каталога, «Пересобрать», восстановление при старте; `reference_sync.py` ← `Store.notify_reference`): для `staff_id` без записи — пустые ФИО (в интерфейсе «Сотрудник ST-xxx»), табельный номер = `staff_id`, аккаунт `EMPLOYEE` со случайным паролем (выдача — «Сбросить пароль»). При загрузке справочников из служебного каталога новые записи получают ФИО-заготовку `data/synth/staff_names.json`. Существующие записи и аккаунты (в т. ч. отключённые) не меняются; записи, которых нет в текущем справочнике, остаются (`in_reference=false`). Выдуманные ФИО не генерируются. Удаления записей нет; `tools\wipe.bat` / `POST /ui/day/reset` справочник сотрудников и аккаунты не трогают.
- **Без БД** (нет `DATABASE_URL`, нет драйвера, БД не ответила при старте) — всё как раньше, в JSON-файлах. Если БД недоступна именно при старте, процесс остаётся на файлах до перезапуска; изменения, сделанные в этом режиме, в БД не попадают (после рестарта с БД действует содержимое БД).
- **Журнал действий.** `actions` пишет middleware: все изменяющие `/ui/*` (в т. ч. reset-password, disable/enable, `POST /ui/directory/staff`, `PUT /ui/settings`, `/ui/auth/login`, `/ui/auth/change-password`) — логин (из токена; для входа — логин после успешной проверки), метод+шаблон, путь, статус, query. Тела запросов и ответов (пароли, `temporary_password`, `initial_password`) не пишутся ни в `actions`, ни в логи. Чтение — `GET /ui/history/actions` (только диспетчер): `limit`, `offset`, `actor` (точный логин), `action` (подстрока, без регистра), `date_from`, `date_to` (YYYY-MM-DD, UTC, включительно).

## Очистка дней (`POST /ui/day/reset`)

- без параметров — все дни: в памяти дни, планы, события, отметки, проигрыватель; в БД (через очередь записи) `DELETE FROM day_state` и `marks` текущих поколений дней; справочники остаются;
- `with_reference=true` — ещё и справочники с матрицей (удаляются указатели `service_state['reference'|'matrix']`, тела в `inputs` остаются);
- `date=YYYY-MM-DD` — только этот день: в памяти день, его режимы, отметки и проигрыватель (если он вёл этот день); в БД `day_state` этой даты и `marks` его `load_id`. Другие дни и справочники не трогаются; если день был активным, активным становится самый поздний из оставшихся. Дня нет — 404 `DAY_NOT_FOUND` (повтор тоже 404). Вместе с `with_reference` — 400.

Во всех вариантах архив (`days`, `plan_versions`, `events`, `alerts`) остаётся, факт сброса пишется в `service_state['day_reset']` (`only_date` — для очистки одного дня). Скрипт — `tools\wipe.bat` (меню: день / все дни / всё со справочниками).

## Чего нет (пока)

- Результаты `/ui/scenario/*` и журнал откатов отметок в памяти (`employee_mark_reverts`) не сохраняются (откаты видны в `actions`).
- Если очередь переполнилась при долгой недоступности БД, отброшенные записи журнала не восстанавливаются; снимок дня догоняет состояние при следующей записи.
- Несколько процессов api на одной БД не поддерживаются: кэши аккаунтов/справочника/настроек читаются при старте и не синхронизируются между процессами.
