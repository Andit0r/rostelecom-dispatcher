# Умная диспетчеризация выездных бригад

Решение кейса «Умная диспетчеризация выездных бригад» (Всероссийский хакатон связи 2026, ПАО «Ростелеком»). Регион — только Екатеринбург. Сервис строит план смены для выездных сотрудников (маршруты, визиты, перерывы, пополнение запаса оборудования в сервисном центре), пересчитывает его по событиям в течение дня и показывает результат диспетчеру в веб-интерфейсе. API соответствует спецификации `data/api_spec.yaml` (OpenAPI 3.0.3).

**Функциональность**

- Распределение нарядов и маршруты: PyVRP + жадная вставка и LNS; нераспределённые наряды попадают в `unassigned` с причиной.
- Перепланирование по событиям (новый наряд, отмена, задержка, перенос, недоступность сотрудника и др.): выполненная часть плана не меняется, затронутые маршруты пересобираются; ответ на событие укладывается в требуемые 10 с (фактически около 0,2 с).
- Раннее предупреждение `LATE_RISK` об опоздании и выявление групповых инцидентов на узле доступа (ПГП).
- Интерфейс диспетчера: карта, диаграмма Ганта, списки нарядов и сотрудников, статистика, режимы расчёта, правка справочника, сценарный анализ («меньше сотрудников», запас оборудования, пробки).
- Мобильное API и экран сотрудника: маршрут, отметки «Позвонил → Прибыл → Завершил», «Передать», «Недоступен».
- История версий плана, событий и тревог в PostgreSQL; состояние восстанавливается после перезапуска.

## Быстрый старт для проверяющих

Нужны Docker с Compose; для скриптов `tools\*.bat` — Windows и Python 3.12 (скрипты используют `backend\.venv` либо `python` из PATH, нужны `pydantic` и `httpx`: `pip install -r backend/requirements.txt`).

**1. Запуск** из корня репозитория (первая сборка занимает несколько минут):

```bash
docker compose up --build
```

**2. Адреса**

| Что | Адрес |
|---|---|
| Сайт диспетчера | http://localhost:3000 |
| API (спецификация `data/api_spec.yaml`) | http://localhost:8080 |
| Swagger UI | http://localhost:8080/docs |
| Проверка готовности | http://localhost:8080/api/v1/health |

Сайт стартует после того, как `api` станет healthy (до 2 минут).

**3. Вход.** `/ui/*` защищён паролем; `/api/v1`, `/docs` и `/health` открыты (их используют внешние системы и проверка спецификации). Учётные данные задаются переменными окружения (файл `.env` рядом с `docker-compose.yml` — compose подхватывает его сам; файл в `.gitignore`):

```ini
# .env — вариант 1: свой пароль диспетчера
DISPATCHER_LOGIN=dispatcher
DISPATCHER_PASSWORD=ваш_пароль
DEMO_ACCOUNTS=off

# .env — вариант 2: общий пароль для всех учётных записей (диспетчер demo-dispatcher и сотрудники)
DEMO_ACCOUNTS=on
DEMO_PASSWORD=ваш_пароль
```

Без `.env` compose использует значения по умолчанию: `DEMO_ACCOUNTS=on`, `DEMO_PASSWORD=demo`, `DISPATCHER_PASSWORD=demo` — вход `demo-dispatcher` / `demo` (экран входа показывает подсказку с логинами). Если запускать API без compose, пароль диспетчера без `DISPATCHER_PASSWORD` случайный и один раз печатается в лог:

```bash
docker compose logs api        # строка «[auth] Создан аккаунт диспетчера …»
```

Учётные записи сохраняются в томе `uistate`; чтобы применить новые значения «с нуля», выполните `docker compose down -v`. Не включайте `DEMO_ACCOUNTS=on` на публичном стенде.

**4. Заполнение данными.** После запуска справочники и дни пусты (на сайте «День не загружен»). Два способа:

- Скрипт симулятора (Windows): `tools\demo.bat` — спросит дату дня (Enter — сегодня) и покажет меню: 1 — план на весь день, 2 — поток звонков, 3 — сборка ПГП, 4 — текучка (отказы, задержки, отмены), 5 — всё подряд, 9 — только справочники. Сайт подхватывает день сам (опрос раз в 2 с), версия плана растёт с каждым событием. Скрипт сервер не запускает.
- Вручную в интерфейсе: «Создать день» (справочники подгрузятся из `data/synth`, если их ещё нет), затем вкладка «Наряды» → «+ Новый наряд».

**5. Что увидит проверяющий:** карту с маршрутами и узлами; диаграмму Ганта по сотрудникам; списки нарядов (статусы, причины нераспределённых, «Риск опоздания») и сотрудников; окно «Статистика» (динамика версий плана, загрузка, прогноз длительности); «Режимы» (пробки, совместные наряды, бюджеты расчёта, «Создать день», «Очистить день»); «Данные» (справочник сотрудников с ФИО и «рюкзаком» оборудования); вкладку «Сценарии»; мобильный вид сотрудника (кнопка «Мобильный вид» или адрес `/#/m`).

**6. Очистка:** кнопка «Очистить день» в «Режимах» либо `tools\wipe.bat` (меню: один день / все дни / всё со справочниками; перед удалением спрашивает подтверждение). Полный сброс контейнеров и БД: `docker compose down -v`.

**7. Оговорки**

- Все данные синтетические (`data/synth`, детерминированный генератор); выводы о качестве плана относятся к ним.
- Windows и прокси: используйте адрес `127.0.0.1`, а не `localhost`; если в окружении задан `HTTP_PROXY`/`HTTPS_PROXY`, перед запуском своих команд выполните `set NO_PROXY=127.0.0.1,localhost` (PowerShell: `$env:NO_PROXY='127.0.0.1,localhost'`), иначе будет ответ 502 от прокси. Скрипты `tools\*.bat` делают это сами.
- Мобильное приложение: описание API, авторизации и подключения по сети — [docs/mobile-api.md](docs/mobile-api.md).
- Симулятор без Windows: `python tools/sim/run_sim.py --base-url http://127.0.0.1:8080 --scenario bulk`, подробности — [tools/sim/README.md](tools/sim/README.md).

## Переменные окружения

Задаются в окружении или `.env` рядом с `docker-compose.yml`. Через compose переопределяются: `TEAM_NAME`, `PLANNER`, `PLANNER_DAY_BUDGET_SEC`, `UI_PLAN_BUDGET_SEC`, `TRAFFIC_FACTORS`, `JOINT_ORDERS`, `CORS_ORIGINS`, `AUTH_ENABLED`, `AUTH_SECRET`, `DISPATCHER_LOGIN`, `DISPATCHER_PASSWORD`, `DEMO_ACCOUNTS`, `DEMO_PASSWORD`, `API_KEY`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`. Остальные — при запуске без compose или правкой `environment` в нём.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `TEAM_NAME` | `непалиндром` | Название команды в ответе `GET /api/v1/health` |
| `PLANNER` | `pyvrp` | Планировщик |
| `PLANNER_DAY_BUDGET_SEC` | `60` | Бюджет построения дневного плана; фактический: `min(значение, 0,8·time_limit_sec − 3)` |
| `PLANNER_PYVRP_SHARE` | `0.7` | Доля бюджета на PyVRP, остальное — LNS |
| `PLANNER_BREAK_MODE` | `shift_duration` | Учёт перерыва в PyVRP: `shift_duration`, `shorten`, `client`, `none` |
| `PLANNER_BREAK_SLACK_MIN` | `60` | Запас до конца окна перерыва, мин |
| `PLANNER_MAX_RELOADS` | `2` | Максимум пополнений за маршрут в модели PyVRP |
| `PLANNER_EVENT_DEADLINE_SEC` | `7` | Внутренний дедлайн обработки события, с |
| `UI_PLAN_BUDGET_SEC` | `15` | Бюджет построения плана при «Создать день» и «Пересобрать» |
| `TRAFFIC_FACTORS` | `off` | Пробки по часам (`on`/`off`): время в пути × коэффициент часа выезда из `hourly_factors` матрицы |
| `JOINT_ORDERS` | `off` | Совместные наряды ВЛС (`on`/`off`): выполняют двое, напарник идёт отдельным визитом `ORD-…-B`. Риск для внешней проверки плана — см. «Ограничения» |
| `CLOCK_FOLLOWS_WALL` | `off` | «Время плана идёт по часам» (`on`/`off`): раз в минуту активному дню (если он сегодняшний по Екатеринбургу) уходит `TIME_TICK` с текущим временем. Для работы с внешними системами и симулятором держите `off`: их более ранние события будут отклонены (409). |
| `DATABASE_URL` | не задан (в compose собирается из `POSTGRES_*`) | Подключение к PostgreSQL; без него всё хранится в памяти и файлах |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | `dispatch` | Только compose: сервис `db` и сборка `DATABASE_URL` (спецсимволы пароля url-кодировать) |
| `STATE_RESTORE` | `on` | Восстанавливать состояние из БД при старте (`off` — всегда пустой старт) |
| `STATE_RESTORE_WAIT_SEC` | `5` | Сколько ждать БД при старте |
| `UI_DATA_DIR` | `data/synth` (в контейнере `/data/synth`, только чтение) | Каталог синтетических справочников: источник для «Создать день» без присланных справочников и для скриптов |
| `HISTORY_FILE` | не задан | JSON-история нарядов для прогноза длительности; без неё прогноз учится на завершённых нарядах из хранилища (нужно ≥ 20) |
| `STAFF_DIRECTORY_FILE`, `RUNTIME_SETTINGS_FILE`, `AUTH_ACCOUNTS_FILE` | в compose — том `/state` | Файлы хранилища без БД (справочник ФИО, режимы из интерфейса, аккаунты); при доступной БД данные лежат в ней |
| `AUTH_ENABLED` | `on` | Авторизация `/ui/*` (`off` — всё открыто, для тестов); `/api/v1` не затрагивается |
| `AUTH_SECRET` | генерируется | Секрет подписи токенов |
| `AUTH_TOKEN_TTL_HOURS` | `12` | Срок жизни токена |
| `AUTH_COOKIE_SECURE` | `off` | Принудительно `Secure` для cookie |
| `DISPATCHER_LOGIN`, `DISPATCHER_PASSWORD` | `dispatcher`; в compose пароль `demo`, без compose — случайный | Диспетчер при первом запуске |
| `DEMO_ACCOUNTS`, `DEMO_PASSWORD` | в compose `on`, `demo`; без compose `off`, `demo` | Общий пароль для всех учётных записей (диспетчер `demo-dispatcher`) |
| `API_KEY` | не задан | Необязательная защита `/api/v1` заголовком `X-API-Key` (кроме `/health`) |
| `CORS_ORIGINS` | dev-адреса фронта | Разрешённые origin через запятую (`*` — только явно) |

Режимы `TRAFFIC_FACTORS`, `JOINT_ORDERS` и бюджеты можно менять в интерфейсе («Режимы»); значения процесс-глобальны, действуют на следующую пересборку и новые события и затрагивают в том числе `/api/v1`. Приоритет: правка из интерфейса → окружение → умолчание.

## Эндпоинты

- `/api/v1` — спецификация `data/api_spec.yaml`: `GET /health`, `PUT /reference`, `PUT /reference/travel-matrix`, `PUT /days/{date}`, `POST /days/{date}/plan`, `GET /days/{date}/plan`, `POST /days/{date}/events`. Имена полей, типы и коды HTTP соблюдаются строго. Всегда открыт.
- `/ui` — наше расширение для интерфейса диспетчера (вне спецификации): создание, пересборка и очистка дня, наряды, история (`/ui/history/*`), справочник сотрудников и аккаунты, сценарии (`/ui/scenario/*`), режимы (`/ui/settings`), прогноз, вход (`/ui/auth/*`). Требует входа. Служебные `/ui/demo/*` нужны тестам и скриптам, интерфейс их не использует.
- `/ui/employee` — API для мобильного приложения сотрудника (`/ui/employee/staff`, `/{staff_id}/route`, `/{staff_id}/marks`); отметки превращаются в события спецификации. Описание: [docs/mobile-api.md](docs/mobile-api.md).
- `/docs` — Swagger UI, `/openapi.json` — схема; обе открыты.

## Данные и скрипты

В программу данные не вшиты: справочники (сервисные центры, сотрудники, узлы доступа с домами, типы работ), матрица времени в пути и наряды приходят по API; всё в интерфейсе строится от последнего присланного справочника. Время плана (`as_of`) определяют данные и события (`now` дня, `timestamp` событий и отметок); системные часы используются только для «Создать день».

Каталог `data/synth` — синтетические справочники (40 сотрудников), матрица (около 16 МБ), история и наборы событий; хранится в репозитории, перегенерация: `python tools/synth/generate.py` (детерминированно, `--help` — опции). Служит для «Создать день» без присланных справочников, `tools\seed.bat`, симулятора и тестов.

| Скрипт (Windows) | Что делает |
|---|---|
| `tools\demo.bat [адрес] [дата]` | Меню симулятора (сценарии 1–5, пункт 9 — только справочники); отчёты — в `out\` |
| `tools\seed.bat [адрес]` | Загружает только справочники и матрицу через `/api/v1`; на сервере стираются все дни и планы; для ФИО запросит логин и пароль диспетчера |
| `tools\wipe.bat [адрес] [дата] [/y]` | Очистка дня, всех дней или всего со справочниками (`POST /ui/day/reset`); справочник ФИО и аккаунты остаются |
| `tools\run-backend-lan.bat` | Запуск backend без Docker на `0.0.0.0:8080` для доступа по сети (см. [docs/mobile-api.md](docs/mobile-api.md)) |

Адрес по умолчанию `http://127.0.0.1:8080`. Без Windows: `python tools/sim/run_sim.py|seed.py|wipe.py --base-url …` ([tools/sim/README.md](tools/sim/README.md)).

PostgreSQL 16 (сервис `db`, том `pgdata`, наружу не публикуется) хранит журнал истории (`days`, `plan_versions`, `events`, `alerts`), снимки дней, отметки, аккаунты и настройки; запись идёт в фоне и горячий путь не тормозит. Без БД сервис работает полностью, но состояние живёт в памяти, а `/ui/history/*` отвечает 503. Схема и восстановление — [docs/db.md](docs/db.md).

## Запуск без Docker

```bash
cd backend
py -3.12 -m venv .venv                 # Linux/macOS: python3.12 -m venv .venv
.venv\Scripts\activate                 # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8080

cd ../frontend
npm install
npm run dev                            # http://localhost:5173, /api и /ui проксируются на :8080
```

Без `DATABASE_URL` состояние хранится в памяти; сборка фронтенда с проверкой типов — `npm run build`.

## Мобильное приложение сотрудника (Android)

В каталоге `mobile-android/` лежит клиент для выездного сотрудника (Kotlin, Jetpack Compose): вход, маршрут на день, карта, отметки о звонке, прибытии и завершении, передача наряда и недоступность. Он работает через `/ui/employee/*` ([docs/mobile-api.md](docs/mobile-api.md)). Адрес сервера задаётся в приложении (для эмулятора Android — `http://10.0.2.2:8080/`). Сборка — Android Studio или `gradlew assembleDebug`.

Приложение учебное и не доведено до конца: часть функций работает нестабильно или не реализована. Основная часть решения — сервис и интерфейс диспетчера; для сотрудника полностью работает мобильный веб-вид (`/#/m`).

## Ограничения и допущения

- Данные синтетические; спрос на INSTALL примерно вдвое больше возможностей 12 инсталляторов, поэтому много `NO_SHIFT_TIME` — это свойство данных, а не солвера.
- Совместные наряды (ВЛС вдвоём, `JOINT_ORDERS`) выключены по умолчанию: такого наряда нет во входных данных, и внешний валидатор плана может засчитать второй визит как нарушение H9. Включайте только для собственных показов.
- Пробки (`TRAFFIC_FACTORS`) выключены: оценка идёт по базовой матрице `durations_sec`; режим доступен в интерфейсе и в сценарии «Пробки».
- Время плана задаётся данными и событиями, а не системными часами.
- Перерыв в PyVRP выражается приближённо (`shift_duration`), место перерыва и пополнение ставит декодер; затем перестановка, жадная вставка, выталкивание и LNS.
- На событиях PyVRP не запускается: жадная вставка и ремонт хвоста маршрута с дедлайном 7 с; межмаршрутной оптимизации на событиях нет. Заморожены остановки со `start < t`.
- Спецификация: `VISIT_DELAYED` и `ORDER_TRANSFERRED` по ещё не начатому визиту возвращают 422; если задержка уводит визит за окно перерыва или смену, нарушение неустранимо и описывается в `EventResult.message` — такие случаи (H2/H3) вынужденные, не ошибка планировщика.
- ПГП определяется правилом «≥ 3 наряда узла за 60 мин»; фоновый наряд узла в пределах 60 мин после инцидента может попасть в группу. `NO_EQUIPMENT` на событиях не выделяется, причины прежних нераспределённых не пересчитываются.
- Прогноз длительности — только справочная информация: в плане остаётся нормативная длительность; на синтетике он не точнее норматива.
- Без БД состояние хранится в памяти и теряется при перезапуске контейнера; с БД оно восстанавливается.
