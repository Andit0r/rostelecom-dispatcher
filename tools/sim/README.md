# Симулятор нагрузки и сквозные проверки API (`tools/sim`)

Внешний клиент по HTTP, как внешний оркестратор: только `/api/v1`, сервер не импортируется и не правится.
Из `backend` берутся лишь модели pydantic и `app/planner/validator.py` (`validate_plan`, `validate_transition`) - для
независимой проверки H1-H10 полученного плана. Состояние дня симулятор ведёт сам по отправленным событиям.
Найденные расхождения и нарушения в серверном коде не чинятся: они попадают в отчёт с seed и шагом.

## Запуск

Интерпретатором `backend/.venv` (нужны pydantic, httpx; данные - `data/synth`):

```bash
backend/.venv/Scripts/python.exe tools/sim/run_sim.py --base-url http://localhost:8080 \
    --scenario all --seed 1 --report out/sim.md
```

| Параметр | Назначение |
|---|---|
| `--scenario` | `bulk`, `calls`, `churn`, `pgp`, `late`, `contract`, `all` или список через запятую (`all` начинает с `contract`) |
| `--seed N` | сид всех случайных выборов (воспроизводимость: те же seed/масштаб/параметры - тот же ход событий) |
| `--report out.md` | markdown-отчёт; рядом пишется `out.json` |
| `--scale 0..1` | доля нарядов обучающего дня (1 - весь день, около 350 нарядов) |
| `--time-limit` | `time_limit_sec` для `POST /plan`, по умолчанию 60 |
| `--quick` | короткие версии сценариев (как в pytest) |
| `--date YYYY-MM-DD` | дата дня для `bulk`, `calls`, `churn`, `pgp`, `late`: один и тот же набор нарядов эталонного дня (демо-день `events_dense.json`, около 282 нарядов к 08:30) переносится на эту дату — все даты и время сдвигаются на одинаковое число суток, идентификаторы `ORD-YYYYMMDD-…` переименовываются, контрольные сроки в рабочих днях пересчитываются по календарю новой даты (как `tools/synth/generate.py --base-date`). Любая дата; на выходной — предупреждение «наряды по рабочим дням», день всё равно загружается. По умолчанию — сегодня по системным часам или ближайший рабочий день. `contract` использует свой день |
| `--native-dates` | без переноса: каждый сценарий берёт свой день из `orders_train.json` (как в pytest) |
| `--calls-single/--calls-batches/--calls-parallel/--calls-empty` | размеры потока звонков; пустой стартовый день |
| `--churn-intensity` | событий в модельный час (по умолчанию 12) |
| `--churn-absent-share` | доля персонала, выбывающего за день (по умолчанию 0.2) |
| `--churn-tick-min` | шаг `TIME_TICK` (по умолчанию 15 мин) |
| `--late-attempts` | число задержек в `late` (по умолчанию 10) |

Код возврата: 0 - все сценарии прошли, 1 - есть находки уровня «провал», 2 - сервер не отвечает.
Для отдельного сервера: `AUTH_ENABLED=off PLANNER_DAY_BUDGET_SEC=10 uvicorn app.main:app --port 8098`, без `DATABASE_URL`.
Каждый `PUT /reference` стирает дни сервера, поэтому гонять симулятор на «боевом» экземпляре с нужным состоянием нельзя.

### Показ на сайте: сборка плана с нуля

Заготовленного дня в интерфейсе нет: показ идёт отдельным терминалом. Сайт диспетчера сам подхватывает день, который
загружает симулятор (опрос `/ui/plan/status`, без перезагрузки):

1. На сайте: «Режимы» → «Очистить день» (`POST /ui/day/reset`, справочники остаются). Появится «День не загружен».
2. В терминале:

```bash
backend/.venv/Scripts/python.exe tools/sim/run_sim.py --base-url http://127.0.0.1:8080 --scenario bulk --time-limit 20
backend/.venv/Scripts/python.exe tools/sim/run_sim.py --base-url http://127.0.0.1:8080 --scenario calls --seed 1
```

   Сайт подхватывает день сам. Windows: используйте `127.0.0.1`, а не `localhost` (IPv6 `[::1]:8080` может быть занят
   `wslrelay`). Если задан `HTTP_PROXY`/`HTTPS_PROXY`, сначала `set NO_PROXY=127.0.0.1,localhost`
   (PowerShell: `$env:NO_PROXY='127.0.0.1,localhost'`) или очистите прокси — иначе симулятор получает 502.

3. Повтор показа — снова «Очистить день». Сохранённый в БД день после рестарта восстанавливается; для чистого старта —
   «Очистить день» или `STATE_RESTORE=off`. Ручной режим без симулятора: «Создать день» и «Наряды» → «+ Новый наряд».

### Служебные скрипты

- `tools/sim/seed.py` (`tools\seed.bat`) — только справочники и матрица из каталога через `/api/v1` (без нарядов и дней) и ФИО-заготовка `data/synth/staff_names.json` для пустых записей справочника сотрудников (`PUT /ui/directory/staff/{id}`, при `AUTH_ENABLED=on` — вход диспетчера).
- `tools/sim/wipe.py` (`tools\wipe.bat`) — очистка через `POST /ui/day/reset`: `--date D` (один день), `--all-days`, `--everything` (со справочниками) или меню; перед удалением печатает, что будет удалено, и спрашивает Y/N (`--yes` — без вопроса).
- `tools\demo.bat [адрес] [дата]` — меню симулятора; дату спрашивает перед меню (Enter — сегодня) и передаёт `--date`.

## Сценарии (`tools/sim/scenarios/*.py`)

| Сценарий | Что делает | Что проверяет |
|---|---|---|
| `bulk` | весь день из `orders_train` одним `PUT days` (+2 сотрудника в `absent_staff_ids`), `POST plan` с `time_limit`, `GET plan`, повторный `POST plan` | схема ответа; H1-H10 валидатором; assigned+unassigned+ПГП+cancelled = вход (H9); множество маршрутов = сотрудники на смене; ПГП против независимого детектора; время <= лимита; `GET` == `POST`; повторный `POST` допустим (идентичность - в метрике, не требование); нет `LATE_RISK` |
| `calls` | поток `NEW_ORDER`: одиночные с паузой 0-3 с, пачки по 5 в один момент, все 8 типов работ (ВЛС, REPAIR, DEGRADATION), повтор последнего `event_id`, затем 10-20 параллельных `POST /events` с разными нарядами + дубль одного `event_id` + 3 параллельных читателя `GET /plan` | после каждого события: ответ <= 10 с, схема, +1 к версии, H1-H10, `validate_transition` (заморозка, NEW_ORDER не раньше timestamp), alerts только пополняются; параллельно: все 200, ровно один принят из дублей, версии идут подряд, итоговый план валиден |
| `churn` | модельный день: `TIME_TICK` каждые N минут, между ними пуассоновский поток событий: новые наряды, `VISIT_DELAYED`/`ORDER_TRANSFERRED` по идущим визитам, отмены (`NOT_CONFIRMED`/`CUSTOMER_REQUEST`), `STAFF_UNAVAILABLE` (до `until` или до конца смены) до заданной доли персонала | H1-H10 + переходы после каждого шага; у выбывшего нет остановок в период недоступности (по модели клиента), `unavailable_from/until` равны событию; отменённые не в маршрутах и в `cancelled`; переданные закрыты, `end` визита = `actual_end`; метрики: размещено/не распределено/причины, пересчёты, латентность по типам, таймлайн |
| `pgp` | 11 подслучаев на одном узле или двух: 2 наряда (нет ПГП), 3 за 50 и ровно за 60 мин (есть), 3 растянутых >60 мин (нет), 4-5 нарядов (группа растёт, `group_id`/`detected_at` не меняются), два узла вперемешку, ПГП уже в первоначальном плане, ПГП на последний наряд при уже распределённых, не-ПГП типы того же узла, ПГП внутри потока звонков, начатый визит ПГП-типа | состав группы, `detected_at` = момент третьего наряда, один `PGP_DETECTED` с `group_id` и `TRANSFER_TO_STATION`, он же в `new_alerts`, наряды вне маршрутов и вне `unassigned`, остальные типы узла не затронуты, H1-H10 после каждого события |
| `late` | (A) идеальный день: только `TIME_TICK` каждые 30 мин; (B) задержка идущего визита, после которой следующий визит сотрудника не успевает к `latest_start` (слот не ближе 45 мин) | A: нет `LATE_RISK` и маршруты не меняются; B: `LATE_RISK` создан не позднее `slot.start - 30 мин` для каждого переназначенного/снятого наряда, `suggested_action` из REASSIGN/RESCHEDULE, `suggested_staff_id`/`proposed_slot` заполнены, `applied` согласуется с планом |
| `contract` | health, повторная загрузка reference/матрицы, ошибки `PUT reference/matrix/days` (400/422), `GET/POST plan` по неизвестному дню (404) и неверным `time_limit_sec` (400), события: невалидные тела (400), 404, 422 по неизвестным order/staff, `until` <= timestamp, не начатый визит, дубль `NEW_ORDER`, `EVENT_OUT_OF_ORDER` (409) и событие раньше `now`, идемпотентность `event_id` (в т.ч. с другим телом), тот же timestamp, смещение `+00:00`, повторная отмена, `POST plan` после первого события (409), пустой день, два дня одновременно, событие на следующих сутках | коды HTTP, формат `ErrorResponse`, схемы `Plan`/`EventResult`/`LoadResult`/`Health` (ручная проверка по `api_spec.yaml`: имена, типы, enum), неизменность состояния после каждого отклонения, отсутствие 5xx |

Возврат сотрудника: спецификация не содержит события «снова доступен» - только `until` внутри `STAFF_UNAVAILABLE`; симулятор
использует его и не симулирует досрочный возврат. Повторные `STAFF_UNAVAILABLE` по тому же сотруднику (смена периода) не покрыты.

## Как читать отчёт

- Заголовок: сервер, seed, масштаб, число сценариев/событий/проверок.
- Сводка: статус каждого сценария (`FAIL` - есть находка уровня «провал»; «замечания» статус не меняют).
- Латентность: по каждому типу запроса `n`, p50, p95, max (реальное время клиента, с).
- Раздел сценария: метрики, примечания и находки. Находка - заголовок, счётчик повторов и до 4 примеров
  `seed, шаг: подробности`; шаг - `#номер событие id` либо имя проверки. Повторить: тот же `--seed`, `--scale`,
  `--time-limit` и `--scenario`.
- Уровни находок: `violation` (нарушение H1-H10 валидатором), `contract` (расхождение со спецификацией),
  `invariant` (нарушение правил раздела 3 и инвариантов симулятора), `latency` (событие > 10 с, план > лимита),
  `error` (исключение сценария, 5xx), `note` (спорное или справочное, не провал).
- H2/H3-нарушения, по которым сервер сам написал в `EventResult.message` «неустранимо: ST-…» (задержка визита выводит
  его за смену/окно перерыва), идут как `note` «вынуждено событием», а не как `violation`.
- `*.json` рядом с отчётом - те же данные машинно (`summary`, `latency`, `scenarios[].findings/metrics`).

## Pytest-обёртка

`backend/tests/test_api_sim.py` поднимает приложение через `TestClient` (адаптер того же интерфейса, что `httpx.Client`)
и запускает быстрые версии всех сценариев (`PLANNER_DAY_BUDGET_SEC=10`, масштаб 0.12, `time_limit 8`, около 35 с).
Тест падает на нарушениях/инвариантах/латентности/5xx и на любых расхождениях со спецификацией, не входящих в список
`KNOWN_CONTRACT_ISSUES` (сейчас пуст). Полный прогон - только через CLI.

```
tools/sim/run_sim.py       CLI
tools/sim/simlib/          client.py (латентность), data.py (данные, фабрика нарядов), schema.py (схемы спецификации),

tools/sim/scenarios/       bulk, calls, churn, pgp, late, contract
```

## Не покрыто

Тело `POST /plan` без `time_limit_sec` (300 с), `409 REFERENCE_NOT_LOADED` (нужен чистый сервер), загрузка 100 МБ,
`hourly_factors`, смена дня в середине сценария, `API_KEY`, схемы запросов проверяются только через ответы сервера
(отдельной валидации исходящих тел нет), JSON Schema из `api_spec.yaml` напрямую не используется (нет jsonschema/PyYAML).
